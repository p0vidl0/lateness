# ADR 001. Один бинарник, две роли, одно состояние

## Решение

Репозиторий собирает один бинарник `lateness`. Роль задаётся аргументом: `serve` или `sweep`. Служебные команды того же бинарника: `invite` печатает ссылку-приглашение, `receiver` — фейк внешних сервисов для e2e. Единственное состояние — Postgres. Отдельной очереди и второго хранилища нет.

`serve` применяет миграции при старте. `sweep` и `invite` только проверяют, что версия схемы равна ожидаемой, и выходят, если схема чужая.

Уведомление сначала записывается строкой `deliveries`, и только потом вызывается SMTP, HTTP или Telegram. Падение между записью и отправкой не теряет решение: следующий проход sweep забирает строку снова. Повторного уведомления за ту же просрочку нет: на переход одна строка на outlet.

Probe выполняет тоже `sweep`: забирает строку с арендой (`probe_at` сдвигается на время аренды), делает запрос вне транзакции и пишет результат с проверкой версии ожидания.

## Почему так

Две роли разделяют приём запросов и фоновую работу, но им не нужны разные модули и разные схемы. Один владелец миграций убирает гонку «кто накатывает таблицы». Строка доставки переживает рестарт процесса, который уже решил, что окно закрыто.

Часы в сценариях — интерфейс, чтобы интеграционный тест двигал время без пауз.
